Why I built this

Google Maps gives you an ETA. It doesn't tell you if you can actually catch the bus

A normal Singapore commute meant Google Maps for the route, SGBusTiming to check whether the bus was actually where Google said it was, and a quick look at the weather app to decide whether today was a walk day or a bus day. Three apps, every morning, to answer one question: what's the fastest, least risky way to get to where I'm going?

That's the idea behind Ripple Transit. It's a Singapore commute planner that pulls live bus arrivals, transfer risk, weather, and MRT status into one screen instead of five. I think of it as how I'd rebuild Google Maps if it were built for one specific person: a time-optimising, comparison-driven Singaporean commuter. That's not a knock on Google. Their global map is genuinely excellent, but a product built for the whole world can't lean into the handful of things that actually decide a Singapore commute: whether the next bus is really coming when it says, whether a transfer is tight or comfortable, and whether it's about to rain on you.

It's also the second product in what I'm calling the Ripple series. The Daily Ripple tested whether I could run an agentic AI system end to end in a financial services context. Ripple Transit tests the same question in a completely different one: real-time, consumer-facing, and judged the moment it gets a bus arrival wrong.

Decisions worth explaining

The parts I'd want you to ask me about

Why I moved off the original spec's MySQL/TiDB and Manus OAuth

The build brief I wrote for this assumed the Manus platform, so it called for MySQL/TiDB and Manus OAuth by default. Once I was actually building for a plain Node service on Render, that assumption stopped making sense. I moved the database to libSQL/SQLite on Turso, one dialect for zero-setup local dev and a cloud deploy, same six tables plus sessions. Auth became plain email and password with bcrypt and httpOnly cookies, self-contained, nothing external to depend on. Small deviation, but a real one: the platform you assume when you write the spec isn't always the platform you actually ship on, and it's worth catching that early rather than fighting it later.

Ask Ripple only fills in what you actually said

The natural-language search box turns a sentence into structured From/To/mode/time fields using Claude Haiku 4.5 with a strict JSON-schema output. The system prompt explicitly forbids inventing a destination, time, or preference you didn't state: unstated just means null. Every ETA, fare, and CO2 figure downstream still comes from the deterministic backend, never from the model. After what The Daily Ripple taught me about a model confidently getting a number wrong, I wasn't going to let this one guess at facts either. It's allowed to parse. It's not allowed to compute.

The taxi estimate that quietly lied for weeks

The fare estimator only ever showed the metered fare (flag-down plus distance) and explicitly excluded surcharges. So a Changi Airport trip or a peak-hour trip read well below what the meter would actually charge. A real test case: Changi T1 to Coronation Road priced at roughly $22.71 base when it should have read closer to $28.71 once the airport surcharge was added. Fixed it by estimating the common LTA surcharges (peak hour, late night, the flat Changi surcharge) and showing them as an itemised, labelled line rather than folding them silently into one number. It's still an estimate, ERP and event surcharges aren't modelled, but now it says so.

An "8 hour 32 minute" route isn't a better route

Re-routing mid-journey near the last train or bus of the night was offering OneMap's "wait for the first morning service" itinerary and showing it verbatim as the recommended alternative. Technically correct, practically useless. I added a sanity guard: only offer an alternative within roughly double the original remaining time, or plus 30 minutes for a missed connection, and if nothing sensible exists, say so honestly instead of surfacing an 8-hour plan. Also renamed the button from "Better route" to "Alternative from here," since it isn't always faster, just what's available.

Stale data that looked exactly like a broken app

The "nearby places" panel appeared to stop working after the first use. Switching category kept the previous category's results under the new label, because a caching setting kept old data visible while new data loaded, and if that new request was slow or rate-limited by data.gov.sg, the stale rows just sat there indefinitely looking like an answer. Fixed by clearing to a loading state on every switch instead of holding onto old data, and by adding an explicit, recoverable error message instead of silently showing something wrong. A UI that shows old data instead of no data reads as broken, even when nothing actually crashed.

What I'd do differently

If I started this over

  • →Log API cost and usage automatically, from the first commit. HERE has a hard cap enforced in code because it's metered and I was watching it closely. The Anthropic calls behind Ask Ripple aren't logged the same way yet, so I'm estimating that cost instead of reading it off a table, which is the same mistake I made on The Daily Ripple.
  • →Write the sanity guard before the feature ships, not after a live bug shows you needed one. The 8-hour re-route alternative was technically correct output from OneMap. It took an actual overnight edge case for me to realise "technically correct" and "useful" aren't the same bar.
  • →Loading and error states are part of the feature, not a detail to add later. The nearby-places bug wasn't really a data problem. It was a missing "this failed, tap to retry" state that let stale data pass as current for anyone who hit a slow response.
  • →Decide upfront which numbers are facts and which are estimates, and never blur the two. The taxi surcharge bug happened because "the fare" quietly meant "the fare minus surcharges" with no label saying so. Every number in the app should say what kind of number it is.

Why I think this matters beyond a route planner

A context-aware decision layer, not a transport aggregator

Take away the Singapore-commute framing and what's left is: fuse several live data streams into one view, weigh the options against preferences someone actually stated instead of one fixed "best" answer, use an LLM strictly as an interface layer bounded by a deterministic backend, and give an honest confidence read (OK, tight, miss) instead of a single number you're expected to trust blindly. That's the same shape as flagging an operational risk with a confidence label instead of a blanket alert, or weighting a recommendation to a client's stated preferences instead of handing back one generic answer.

The part I think actually transfers: an LLM is useful as a parser and a translator of intent, not as the source of the numbers people are going to act on. Ask Ripple can read "get me to Changi by 6, I hate crowds" and turn it into structured fields. It never gets to invent the ETA, the fare, or the crowding level itself. That boundary, model interprets, deterministic system computes, is the one lesson I'd carry into any enterprise AI workflow, financial services or otherwise.
